## Assessment of the prototype

The chosen architecture is credible for the approved slice. A coordinated APEX Main checkpoint, whole configured application/schema export, reviewed Git diff, native staging/verification, manual change PR, semantic squash merge, generated release PR/tag/changelogs and separate manual deployment are distinguishable operations. The project does not claim that Git exports only the edited page, that Foundation/Hello/World are native mini apps, or that PR checks establish Oracle behavior. These distinctions agree with the inspected implementation.

The release path has only `workflow_dispatch`, a `main` job condition, the `e3-lab` environment and a dedicated local runner. PR checks and Release Please use hosted runners and do not receive database secrets. Deployment and qualification share a repository concurrency group. The application is checked out at the selected release while control SQL comes from the dispatch revision of `main`; this is documented and is not an immutable promotion service. For the reviewed reference runs, the controller and application identities both resolve to the pinned application SHA.

The workflow requires a positive `Errors: 0` result before packaging or target writes and scans configured Oracle/client diagnostics. This is materially better evidence than SQLcl process status alone: the retained version-mismatch experiment explicitly records a zero process exit with a native rejection. `WHENEVER SQLERROR` and `exit success` do not make every PROJECT diagnostic a reliable exit status. The manual correctly requires inspection of capture/stage/verify results. Error detection remains bounded rather than a general SQLcl diagnostic guarantee.

Native PROJECT/Liquibase is the migration authority. The application changelog uses the supplied APEX mapping and a `runOnChange` APEX changeset. The initial-data changeset supplies declared literal demonstration data, guards `E3_TARGET`, and refuses a populated initial target; it is not an export of developer business rows. The current source and staged APEX export have no recurring Python adapter. All executable/configuration files shared between the parent example and bundled application match byte-for-byte; the example README differs as an orientation document.

The custom `LAB_RUNTIME.assert_ready` checks fixed lab state and component versions. It is not native semantic dependency management. `accept.sql` checks the retained region heading, executes an APEX session initialization and publishes availability. A replay changes the page title, which is checked separately in the browser; the SQL acceptance check does not validate that new title. The final publication workspace lookup uses the schema argument, but the documented lab intentionally has schema and workspace both `E3_TARGET`. This disclosed restriction does not invalidate the fixed lab and must be corrected before supporting unequal names.

The supported starting state is an already prepared E.2/E.3 database/APEX/ORDS lab with existing author and target applications and authorized accounts. Startup retains those resources. The materials expressly do not claim clean-host reconstruction, and PBI-054 retains that proof. I do not require new provisioning infrastructure for E.3 handover. R1-L1 concerns contradictory present instructions, not completion of PBI-054.

## Findings

### R1-M1 — Make the presentation's operating commands select the operator's LAB

**Locations:** Parent `progress/E.3/sprint_E.3_increment_demo.pptx`, slide 4 and its notes, and slide 10; corresponding authoring source [build.mjs lines 38–40 and 57](https://github.com/rstyczynski/APEX_CICD/blob/b695ec9627f1453220a04032563f812242f7ac0f/progress/E.3/presentation-handover/build.mjs#L38). Launcher defaults: [scripts/e3-runner.sh lines 7–15](https://github.com/rstyczynski/APEX_CICD/blob/b695ec9627f1453220a04032563f812242f7ac0f/scripts/e3-runner.sh#L7). Current operator sequence: walkthrough steps A/B/F, particularly lines 426–443, 502–527 and 1096–1106.

**Observed facts:** Slide 4 presents `./scripts/e3-runner.sh setup` and `./scripts/e3-runner.sh`, with the default `~/actions-runner-e3` directory. The script defaults to `rstyczynski/APEX_CICD_E3`; it does not consume the walkthrough's `e3_repo` shell variable unless `--repo` is passed. Slide 10 displays a dispatch to that same seed repository for fixed tag `v1.0.4`. The current walkthrough instead requires every participant, including the seed owner, to use their own `APEX_CICD_E3_LAB`, explicit `--repo`/`--directory`, and the newly generated tag. The Markdown historical section clearly labels the old commands, but the deck's slide 4 instructions do not carry that distinction. Its notes point to the historical runner chapter.

**Impact on E.3:** Following the presentation alongside the current walkthrough can register/start the wrong repository's runner, leave the LAB job waiting, fail authorization for another operator, or direct an authorized seed owner to dispatch the wrong repository/version. This is a concrete inconsistency in the delivered operating pair, independent of production hardening. No such dispatch was performed in this review.

**Proposed correction:** Use the same explicit LAB repository, runner directory and selected published tag in slides and notes as in the current walkthrough. Keep the recorded seed run as a clearly labeled historical observation, separate from copyable dispatch instructions. Synchronize the presentation authoring source.

**Acceptance check:** Extract the revised deck's commands/notes and compare them with steps A/B/F. A reviewer must be able to resolve every mutation to the selected LAB and its chosen tag; seed-specific commands must be visibly historical. Render and inspect the changed slides. This correction does not require redeploying the seed.

### R1-M2 — Identify seed-evidence checks accurately or bind them to the selected replay

**Locations:** [tests/integration/test_pipeline.sh lines 3–24 and 31–43](https://github.com/rstyczynski/APEX_CICD/blob/b695ec9627f1453220a04032563f812242f7ac0f/tests/integration/test_pipeline.sh#L3); [tests/smoke/test_platform.sh lines 3–10](https://github.com/rstyczynski/APEX_CICD/blob/b695ec9627f1453220a04032563f812242f7ac0f/tests/smoke/test_platform.sh#L3); [user_manual.md lines 243–249](https://github.com/rstyczynski/APEX_CICD/blob/b695ec9627f1453220a04032563f812242f7ac0f/progress/E.3/user_manual.md#L243); `docs/test-profile.md`, “E.3 implemented pipeline checks.”

**Observed facts:** Both integration functions hard-code `rstyczynski/APEX_CICD_E3` and read the fixed committed `github-environment-journey.json`, including v1.0.4 and runs 41679427616/41679432928. Platform smoke also hard-codes the seed when reading environment variables. Neither takes `e3_repo` or an operator's newly recorded journey as input. The manual nevertheless describes access to the “selected repository.” Downloading evidence into a fresh temporary directory does not make the underlying deployment or qualification run fresh.

**Impact on E.3:** A successful invocation can validate the old seed evidence while the operator's LAB deployment is wrong or has not occurred. Conversely, an operator able to administer their LAB but unable to read the seed environment configuration may be unable to perform platform smoke. The current source therefore does not substantiate the manual's selected-repository description. The recorded seed checks remain useful and their earlier passes are not invalidated.

**Proposed correction:** The smallest sufficient correction is to label these commands explicitly as reference-run evidence regression, state their fixed repository/run identities and access requirements, and direct replay acceptance to the new run's receipt, logs and browser observations. **Acceptance check:** For the documentation-only option, every current test description must distinguish retrieval of reference evidence from execution/validation of a new LAB journey. For parameterization, a bounded offline check should show that a second repository and its run IDs are used throughout and that seed evidence cannot satisfy the second journey. No additional deployment is requested by this finding.

### R1-L1 — Reconcile the scratch policy with the retained-lab credential instructions

**Locations:** [user_manual.md lines 127–150](https://github.com/rstyczynski/APEX_CICD/blob/b695ec9627f1453220a04032563f812242f7ac0f/progress/E.3/user_manual.md#L127); walkthrough lines 321–333, 648–657 and 1131–1143; handover lines 46–54; [scripts/apex-vm-start.sh line 19](https://github.com/rstyczynski/APEX_CICD/blob/b695ec9627f1453220a04032563f812242f7ac0f/scripts/apex-vm-start.sh#L19), reachable through `apex-start.sh` when the engine is unavailable.

**Observed facts:** The manual says `.local-apex` must never supply credentials, then instructs the developer to retrieve the author password from `.local-apex/e1-secrets.json`. The live walkthrough also retrieves Builder and end-user passwords there. These are labeled legacy lookups, and alternative assigned credentials are acknowledged for another host, but they are still presented as current run steps. Separately, the inherited VM-start fallback injects `.local-apex/containers.conf` as `CONTAINERS_CONF_OVERRIDE`, without generating it. The normal walkthrough starts the VM first, so this fallback need not run during the intended path.

**Impact on E.3:** The workflow's temporary-connection design is correctly separated from these local dependencies, but the categorical handover/manual wording obscures what can safely be discarded and what a prepared operator must supply. This is a documentation/policy-boundary defect, not evidence of leaked credentials or a failed reference deployment. The explicit prepared-lab limitation makes its severity low.

**Proposed correction:** Make authorized operator-supplied credentials the current instruction and move legacy file lookups into clearly historical context. Scope workflow independence claims precisely. Document the inherited startup fallback's dependency or remove that dependency in a separately authorized correction. Do not migrate/delete private records merely to close this review, and do not turn this into a demand for full fresh-lab provisioning.

**Acceptance check:** A static walkthrough review should be able to follow supported startup, sign-in and native profile setup with already assigned credentials and no credential/configuration authority in checkout scratch. Any retained historical dependency must be accurately delimited; preservation of old evidence remains explicit.

### R1-L2 — Require the negative result to identify the expected failing rule

**Locations:** Application [.github/workflows/qualification.yml lines 67–75](https://github.com/rstyczynski/APEX_CICD_E3/blob/fbda57a0cbe4d32961ad826852bd04394a500c11/.github/workflows/qualification.yml#L67), mirrored in the parent example; parent `tests/integration/test_pipeline.sh` lines 41–43. Compare the stronger assertion in walkthrough chapter H's manual exercise.

**Observed facts:** The automated check requires absence of `Errors: 0`, then searches for either `stagechangelogfilesvalid` or `stagechangelogcomplete` anywhere in the negative log. Those names also appear on successful INFO rows in the positive log. A nonzero-error report caused by another verification rule can therefore meet the predicate while the named stage rules have passed. The receipt would still assert `missing_changeset_rejected:true`. The parent IT-2 reader repeats the same loose check. The CLI exercise already requires `ERROR` on the `stagechangelogfilesvalid` row.

**Impact on E.3:** This is a source-inspected risk of misclassifying the architecture experiment's result. It does not discredit the saved reference negative log: that log actually reports `Errors: 1`, an ERROR on `stagechangelogfilesvalid`, and the deleted `e1_dev_c/package_bodies/lab_runtime.sql` path. Qualification contains no deployment operation, so this weakness does not create a path to deploy its damaged checkout.

**Proposed correction:** Require an ERROR on the intended missing-file rule, a positive error count and the selected missing path, with appropriate handling of SQLcl formatting. Treat unrelated failures as failed experiments. Align the workflow, evidence reader and manual assertion.

**Acceptance check:** A small offline log-classification check should accept the retained missing-file result and reject a zero-error result, an unrelated-error result with INFO stage rows, and an incomplete/connection-failure log. This review did not execute such tests.

## Explicitly deferred production and broader Elaboration work

These are recommendations for later selection, not new backlog assignments or Product Owner dispositions:

- **Independent infrastructure/operator reproduction:** PBI-054 remains appropriate. It should cover full lab provisioning and account/configuration acquisition; correcting the current handover inconsistencies does not require completing it.
- **Toolchain admission and upgrades:** The reference application records SQLcl release 25.4.1.0 and the action pins build 25.4.1.022.0618 plus its checksum. Developer selection checks release, but does not enforce the full build and merely prints a message when selection fails. The controller action installs one fixed build rather than selecting a toolchain for arbitrary historical tags. Complete NFR-5 nonzero pre-operation admission and upgrade/redeployment evidence before claiming production compliance. The actual reviewed fixed pair matches; the retained mismatch experiment is not full gate qualification.
- **Identity, drift, maintenance and recovery:** Preserve the existing PBI-020/021/022/023/024/028/029/037/038/045 follow-up. Same-name schema guards do not establish database-instance ownership. Repository concurrency does not fence other repositories, direct clients or active requests. APEX import may restore availability before restriction is reapplied, mapped imports may affect component identity, and committed DDL is not automatically rolled back. These are disclosed boundaries for this disposable serial lab.
- **Release trust and traceability:** Protected refs, independent review/attestation, explicit controller/configuration/tool-build identity in durable receipts, immutable qualified-byte promotion and rejection of stale evidence remain necessary before broader use. Current tag syntax, ancestry, published-release and version checks are useful but do not establish that service. Resolve the exact tag ref unambiguously when hardening admission.
- **Application correctness and contracts:** Broader authenticated browser coverage, saved reports/user state, schema drift, semantic component compatibility and real multi-developer contention remain separate proofs. Fixed LAB_RUNTIME versions and a stable region/session check must not be generalized into comprehensive compatibility or business validation. Mini-app reuse remains proposed PBI-044 work.
- **Setup cost:** PBI-055 may optimize repeated tool setup after measuring it, while retaining build integrity, compatibility and per-job private connections. It is not a prerequisite for this prototype.
