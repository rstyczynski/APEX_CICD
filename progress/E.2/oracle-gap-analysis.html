G, H and I — native support gaps

“Not supported” below refers to the specified automatic capability in the evaluated APEX/SQLcl PROJECT workflow.

Scenario Native support Consequence
G: component version dependency protection Not supported. Clean PROJECT verification accepted both allowed and conflicting component declarations. Keep explicit component contracts and supplementary compatibility admission. Evidence
H: automatic live-drift deployment protection Not supported by the evaluated delivery path. No qualified automatic comparison/rejection gate was supplied. Require application/schema/code comparison against the accepted target baseline before deployment. The zero-change replay did not test overwrite protection. Evidence and limits
I: automatic failed-deployment repair Not supported. PROJECT does not design the repair. Inspect partial state and supply a reviewed forward repair. SQLcl/Liquibase can deliver that repair, but E.2 did not exercise the E.1-equivalent recovery scenario.

APEX subscriptions provide shared-component reuse and propagation, not our component SemVer admission. Oracle APEX 24.2 subscriptions. Reviewed repair uses changeset execution/history, not automatic repair. Oracle Liquibase update.

Blockers and corrections

  • Release qualification: SQLcl 25.3 verification failed on the retained F distribution. A clean 25.4.1 comparison passed, but does not certify the old artifacts. Select a pinned client and regenerate/verify a consistent release. Correction receipt.
  • Packaging: post-stage APEX edits create source/distribution inconsistency. Express release configuration before capture or through qualified deployment hooks.
  • Identity: mapped replacement changed APEX region IDs in the earlier fixture. Qualify required identity and saved-report preservation before adoption. Detailed observations.
  • Recovery: reviewed partial-failure repair remains missing E.2 validation; this is an implementation gap, not proof that Oracle cannot deliver repairs.

No evidence establishes general incompatibility between PROJECT, Working Copies and Git. Repository coexistence is feasible; source layout and migration ownership must be explicit. Use one migration authority per target delivery stream.

Policies and unnecessary custom mechanisms

  • Reevaluate E.1's break-glass authoring and component-wide reservations. They are project policies; they do not prohibit native Working Copy authoring.
  • Prefer native capture, staging, packaging, mappings and access controls. Do not rebuild these inside another custom controller.
  • E1_CTRL is not wholly redundant: qualification/provenance, ownership, drift admission and repair governance need separate decisions.
  • Define component contracts and major/minor/patch rules, including LOV return values and retained-data expectations. Automatic classification is not required for Elaboration.
