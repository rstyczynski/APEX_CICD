## R1-M1 — Establish a trusted first checksum baseline

**Location:** Design lines 167–180 and IT-3; E.3 `tests/release-correction/integration.json`; architecture AI-6.

The design captures the current target checksum and verifies baseline identity against the last successful receipt. The cited E.3 receipt records source/archive identities and preservation results, but contains no application metadata checksum or checksum profile. Matching the old source identity to that receipt does not establish that today's live metadata still matches that installed source. A pending edit made before the new baseline capture could become part of the accepted baseline and survive every subsequent equality check until deployment overwrites it. IT-3 only tests an edit introduced after baseline creation.

The existing instruction to block on missing or unexplained evidence is safe. However, it leaves the described prepared-target entry path unresolved: either the experiment stops, or an implementer could treat the new observation as sufficient evidence of cleanliness. I did not establish that no private qualifying evidence exists; the design must identify and validate it if it is the intended prerequisite.

**Impact on this sprint:** PBI-042's pending-work protection depends on comparing against trusted accepted content, not merely against an earlier observation in the same run. This affects the chosen retained target directly, without requiring general schema drift detection.

**Proposed correction:** Specify one first-run baseline qualification path before any candidate installation. Identify a retained trusted checksum/profile if available; otherwise reconcile a diagnostic export of the live target against the exact last-installed accepted APEX source using a documented identity/target-settings normalization and explicit review of all differences. Preserve raw evidence. Unknown content remains blocked; do not import the old archive merely to obtain a clean baseline. Bind the approved baseline to target identity, source/archive, checksum options and application state, and retain it between attempts rather than recapturing it as authority on each admission.

The documented APEX checksum is independent of IDs, but that alone does not establish equality for all target-specific settings or prove a current live export is accepted source. [Oracle APEX 24.2 GET_APPLICATION](https://docs.oracle.com/en/database/oracle/apex/24.2/aeapi/GET_APPLICATION_Function.html).

**Acceptance check:** The revised design identifies the exact baseline evidence or reconciliation procedure and its stop condition. Planned execution must show two unchanged reads under the chosen profile, rejection of an unexplained difference already present at admission/baseline qualification, and preservation of that difference without deployment or silent rebaselining. This can be a bounded extension of IT-3, not a new framework. If the prerequisite cannot be established, record PBI-042 execution as blocked.

## R1-M2 — Reconcile availability and checksum lifecycle with native import

**Location:** Design lines 163–172 and 194–202; inherited [release workflow](../../examples/git-pipeline/.github/workflows/release.yml) lines 93–110; [restrict.sql](../../examples/git-pipeline/sql/restrict.sql), [accept.sql](../../examples/git-pipeline/sql/accept.sql); committed E.3 archive member `releases/apex/f810003/f810003.sql`, line 100.

The design states that the application remains unavailable throughout synchronization and that native failure keeps it unavailable. The inherited workflow explicitly recognizes that import can restore the source application's availability and reapplies restriction after deployment. The inspected committed archive has `p_flow_status=>'AVAILABLE'`. Consequently, pre-import restriction alone does not support the uninterrupted-unavailability claim; failure after an import but before the later restriction can also leave a different state. This is already visible in retained source, not a hypothetical demand for production fencing.

There is a related receipt-order ambiguity: the design records the new checksum before restoring intended availability. It does not specify whether the checksum profile is stable across these status changes, or how the next admission compares the restored application with that receipt. I have not run the checksum/status experiment and do not assert that status definitely changes this checksum. It must be resolved explicitly instead of assumed.

**Impact on this sprint:** The positive/repeat procedure and failure instructions promise a target state that the selected inherited operations do not establish. An ambiguous post-success fingerprint can also make the next clean admission fail or encourage unsafe rebaselining.

**Proposed correction:** Use the already selected coordinated no-user/no-author interval as the bounded operational exclusion and describe technical availability separately. State that native import may restore availability, when restriction is reapplied, how actual state is observed after errors, and that a failure does not prove the target stayed unavailable. Keep participants excluded until a reviewed recovery decision. If continuous technical denial is truly required, specify a supported control that survives import and qualify it; this stronger control is not required merely to retain the bounded experiment.

Specify the order of baseline capture, temporary restriction, import, checks, restoration and receipt finalization. Qualify checksum behavior under those states and bind the successful receipt to the state used by subsequent admission; do not indiscriminately normalize away unexplained metadata differences. Split the inherited acceptance/publication operation if needed so its availability change cannot precede required preservation/acceptance checks unnoticed. Oracle documents application status as a mutable setting, not an import-spanning lock. [Oracle APEX 24.2 SET_APPLICATION_STATUS](https://docs.oracle.com/en/database/oracle/apex/24.2/aeapi/APEX_APPLICATION_ADMIN.SET_APPLICATION_STATUS-Procedure.html).

**Acceptance check:** Revised prose and IT-4 identify actual status transitions and a coherent receipt/checksum comparison state. Planned rehearsal observes status and checksum around restriction, import and restoration, and confirms the subsequent repeat admission works without adopting a new untrusted baseline. Failure instructions require observing/reporting actual state and maintaining coordinated exclusion; they must not infer unavailability from the fact that deployment failed.

## Other review conclusions

- **Native stage/release semantics:** The explicit immutable comparison bases and source-before-stage commits are appropriate. Oracle documents stage's branch option as the comparison branch and release as moving upcoming work into a numbered release. The design correctly requires inspection of actual generated includes rather than assuming three independent application imports. [SQLcl 25.4 PROJECT reference](https://docs.oracle.com/en/database/oracle/sql-developer-command-line/25.4/sqcug/project.html).
- **Dependencies/conflicts:** C's dependency is an integration/release acceptance dependency, not a database execution dependency. That is sufficient for the selected criterion to explain coordination and ordering, provided the walkthrough shows actual source/include relationships and the order used. No forced textual collision or new DDL dependency is needed for design approval. If no collision occurs, report that and explain how shared include changes were reviewed; do not claim conflict-resolution validation. The current stop rules already require preserving all three intents and verifying actual output.
- **Operator refusal:** An explicit operator can demonstrate the selected stale/unsafe-refresh cases under controlled exclusion. It does not establish unattended refusal or racing-worker safety. The design's negative-case evidence and explicit limitations are appropriately scoped. Final rechecks must cover the selected release/source and the live baseline as described; native PROJECT verify supplies neither target drift detection nor atomic admission.
- **Prepared target and toolchain:** Reusing E3_TARGET/810203 for a supported upgrade is reasonable. The inherited initial-data guard and absence of fresh-install qualification are disclosed. No new environment, historical changeset rewrite or tool-version bypass is needed. Actual identities, qualified build and selected Git metadata still need preflight; historical E.3 success cannot supply an E.4 pass.
