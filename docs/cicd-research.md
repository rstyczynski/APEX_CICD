## Evidence and alternatives

The supplied [Oracle paper](../refs/apex-lifecycle-management-v3.pdf), *Understanding the Oracle APEX Application Development Lifecycle*, is June 2025, version 3.2, despite its filename. Page 2 states that its examples use APEX 24.2 and SQLcl 25.1.1. Pages 18–20 explain PROJECT export/stage; pages 26–30 cover packaging and target mapping; pages 40–44 show automation. Figure 26 on page 29 was visually inspected: separate workspaces and schemas can share an instance, with distinct application IDs. This supports a modest local topology, with a shared failure boundary. The paper remains unchanged.

**SQLcl PROJECT** provides export, branch comparison, generated changesets, release packaging, and deployment. It is the strongest integrated alternative and fits the paper directly. It reduces custom orchestration but introduces snapshot/stage conventions and generated schema differences that still need review. It does not remove target mapping, data-migration design, or recovery testing. For this lab, explicit migration intent makes the database-change lesson easier to inspect. Reconsider PROJECT if maintaining the explicit release controller becomes more work than its conventions save. See [SQLcl 25.3 PROJECT](https://docs.oracle.com/en/database/oracle/sql-developer-command-line/25.3/sqcug/project.html) and [25.3 CI/CD introduction](https://docs.oracle.com/en/database/oracle/sql-developer-command-line/25.3/sqcug/introduction.html).

**Split export plus explicit migrations**, the proposed choice, separates APEX metadata snapshots from database evolution. A complete split export is reviewable by page/component; SQLcl can suppress export dates and retain original IDs. Use full application releases initially, rather than selective component deployment with deletion/dependency ambiguity. Hello and World are functional boundaries, not separate release units. The cost is a small controller that orders migration, application import, configuration, and checks. See [APEX 24.2 export options](https://docs.oracle.com/en/database/oracle/apex/24.2/aeadm/exporting-one-or-more-applications.html).

**Liquibase integration** supplies changeset tracking and locking without inventing a migration ledger. Use an XML root changelog with explicitly ordered formatted SQL files; keep application import outside that ledger and make its repetition testable. Preserve applied migrations; correct them with new changesets. Standalone Liquibase would add extension/JDBC version management without a demonstrated benefit here. SQLcl's standalone distribution includes the feature; its deployment privileges and tracking tables must be provisioned in each dedicated application schema. See [25.3 requirements](https://docs.oracle.com/en/database/oracle/sql-developer-command-line/25.3/sqcug/requirements-using-liquibase.html), [bundled feature](https://docs.oracle.com/en/database/oracle/sql-developer-command-line/25.3/sqcug/liquibase-sqlcl.html), and [open-source changesets](https://docs.oracle.com/en/database/oracle/sql-developer-command-line/25.3/sqcug/liquibase-open-source-changesets-sqlcl-liquibase.html).

**APEX Supporting Objects or manual scripts** can bundle schema setup with an app. They are credible for tiny installations, but mixing two migration authorities would obscure history and rerun behavior. Exclude supporting objects from the chosen export and let Liquibase own database evolution. Manual GUI export/import remains an emergency inspection aid; it does not demonstrate the required repeatable automated checks and promotion.

**Runner choice.** A local shell pipeline can retire connectivity and delivery risks in E.1. For the release, propose GitHub Actions on a dedicated self-hosted macOS runner on this host, because the services bind to loopback. A hosted runner cannot directly reach this Mac's loopback; exposing database ports or adding a tunnel is unnecessary scope. Jenkins is viable but adds a controller to maintain. GitLab or Oracle VB Studio would add a service without a current project need. Self-hosted runners require maintenance and may retain state; only trusted reviewed jobs may access deployment credentials. Registration, workflow publication, and remote execution are later authorized work. See [GitHub runner model](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners).

## Version and recovery limits

Propose SQLcl **25.3.0.274.1210** with Java **21**, not a moving latest download. Its [release notes](https://www.oracle.com/tools/sqlcl/sqlcl-relnotes-25.3.0.html) document Java 17/21 and fixes affecting APEX/Liquibase and PROJECT exports. Those fixes are reasons to test the selected combination, not evidence of a current defect in this environment. The host currently has Java 25.0.1 and no SQLcl command on PATH. E.1 must install or locate an isolated compatible Java runtime, record its exact patch and SQLcl archive checksum, and verify help and actual error propagation before deployment. Do not upgrade APEX to match newer documentation; APEXlang and 26.1-only features are outside this baseline.

An APEX import may replace an existing application. Target workspace, schema, ID and alias must be checked before import; see [APEX 24.2 installation](https://docs.oracle.com/en/database/oracle/apex/24.2/aeadm/installing-an-application.html). Database DDL can commit implicitly, so a failed release is not automatically atomic. The [26ai SQL reference](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/COMMIT.html) documents that behavior. Prefer additive migrations and forward repair; restore a prior APEX artifact only when compatible with the resulting schema. Do not promise that Liquibase rollback restores greeting data.

## Parallel development, page fixes and Git integration

### What the supplied paper covers

The previous draft covered export granularity but did not adequately model concurrent developers. This is a material gap in the proposed baseline, now addressed by UC-7 and FR-8 in the SRS. The supplied paper explicitly covers simultaneous editing and page locking on pages 12–14, modularization on 15–16, team-centric versus feature-centric development on 32–34, conflict resolution on 36–38, integration back into central DEV on 39, and automation on 40–44. These are proposed workflows supported by documentation, not experiments run in this lab.

In APEX terminology a developer edits a **Page** in **Page Designer**, including its regions, items, validations and processes. A page fix can use a **Working Copy** of the application. SQLcl also supports selected-component exports, such as `PAGE:3`; this is a transport granularity, not a guarantee that the page has no shared-component or database dependencies. Our versioned Hello/World modules are logical product components. An APEX **Component Group** groups certain Shared Components for copy/subscription/refresh; it is not a general bundle of pages, migrations and module versions. See [24.2 Component Groups](https://docs.oracle.com/en/database/oracle/apex/24.2/htmdb/using-component-groups.html) and [selected exports](https://docs.oracle.com/en/database/oracle/apex/24.2/aeadm/exporting-one-or-more-applications.html).

### Two distinct collaboration models

**Shared DEV, team-centric.** Developers edit different pages in a shared application, preferably using page locks and Working Copies for bounded fixes. Integration of a Working Copy replaces selected pages/shared components, can overwrite newer Main changes, and requires explicit deletion handling. Application properties and other component types have merge limitations. A Working Copy is an application copy, not a database/schema branch. Database changes in its shared parsing schema still affect colleagues. Use a coordinated integration owner and serialize schema changes and exports. Git snapshots of shared DEV represent coordinated team checkpoints; do not pretend they isolate each contributor's unrelated live changes. See [Oracle 24.2 Working Copies](https://docs.oracle.com/en/database/oracle/apex/24.2/htmdb/about-working-copies.html).

**Private development area, feature-centric.** Each task pairs a Git branch with an application and schema area restored from the same accepted base. Developers can then edit separate pages, export changes, combine their branches and rebuild the result before review. The paper's strongest isolation uses separate branch instances with matching workspace name/ID and APEX patch level; page 34 proposes PDB cloning or a matching independent installation. Separate workspaces/schemas on one instance save resources but require different identities and proven export normalization; they are not silently equivalent. A Git branch alone does not isolate APEX dictionary state, schema DDL or greeting data.

### Git protocol proposed for this lab

Use short-lived task branches from a recorded integration commit; each branch records its corresponding development target. Persist complete split SQL exports with stable original IDs and suppressed export dates, plus explicit migrations. Review changed pages, shared components, install controllers, component versions and compatibility metadata together. A one-page fix may have a small diff while still producing a complete application release. Selected page deployment remains a separate future choice, with dependency/deletion checks; it is not required for a focused fix.

Bring current integration changes into the task branch before review. Resolve same-page/shared-component conflicts deliberately, then import the combined SQL into a controlled validation target and verify both developers' intended results. Reject conflict markers and duplicate page/component identities. Coordinate new page numbers and shared names before export; do not repair arbitrary internal IDs with search-and-replace. Parallel database migrations require unique IDs, explicit order and a reviewed upgrade path. Component-version labels and the compatibility declaration are shared files that may also conflict.

The paper illustrates both YAML and SQL conflicts. For this APEX 24.2 baseline, keep SQL APPLICATION_SOURCE as the installable authority and READABLE_YAML as an optional review aid; do not assume editing a readable representation updates the deployable files. Oracle distinguishes these export types in [APEX_EXPORT 24.2](https://docs.oracle.com/en/database/oracle/apex/24.2/aeapi/GET_APPLICATION_Function.html). A text merge that Git accepts still needs an import and behavior check. The [Git project's merge documentation](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging) explains three-way merges and manual conflict resolution; APEX semantic validity is an additional project gate.

After review, build from the merged commit and deploy that artifact to central DEV/integration and TEST under target-specific guards. Do not overwrite unsaved shared DEV work: freeze integration, preserve approved work, or use an area with no direct editing. Before the next task, refresh its target from the new accepted baseline. Neither merging Git nor merging a Working Copy implicitly performs the other operation. No merge, push, provisioning or import was executed here.

### Independent public evidence and its limits

Rafał Grzegorczyk's [Pretius Working Copies walkthrough](https://pretius.com/blog/oracle-apex-working-copies) (updated 18 July 2024 for APEX 24.1) demonstrates two developers, separate copies, page-number collisions and application-property merge limits. It corroborates the practical collision risk rather than proving 24.2 behavior. Oracle's 24.2 reference controls version-specific claims; E.1 must reproduce the relevant cases.

The maintainer's [OPAL Tools documentation](https://github.com/daust/opal-tools) describes SQLcl-based APEX/database export, ordered installation and logging. This is an independent automation alternative to PROJECT or a small explicit controller. It adds a tool/distribution to pin and validate; no OPAL release was selected, installed or verified here. Its Java/bundled-library requirements must not be substituted for SQLcl 25.3 requirements. Prefer it only if a scoped trial shows less maintenance than the proposed controller; it does not solve merge semantics or developer isolation by itself.

### Decision and validation still needed

The following profile comparison informed the proposal; the subsequent Product Owner decision below reserves native Working Copies for break-glass use. Recommend feature-centric Git integration for the two-developer merge demonstration, with one controlled integration owner; retain shared DEV/Working Copies as the lower-resource UI alternative with explicit schema-sharing limits. A DEV/TEST-only topology does not supply independent task areas. E.1 must first validate an affordable target layout and stable export identities; additional PDBs/VMs or containers are not authorized by this research. If isolation cannot be achieved with agreed resources, return that limitation for a Product Owner decision.

For normal managed work require concurrent Hello/World page additions, shared bookkeeping/dependency attribution, safe scope expansion, a page deletion and parallel schema changes. Two different pages in the same module still conflict under the selected component reservation rule; same-page text conflicts remain a controlled break-glass/out-of-tool reconciliation case. Rebuild the integrated result from Git and prove both retained changes, version compatibility and preserved history. Research informs these gates; passing a synthetic text merge cannot retire them. This new collaboration risk keeps the toolchain recommendation provisional; PROJECT and explicit migrations must be judged against the same integration cases before claiming viability.

The implementor recommends the organizing workflow: developers work on task branches merged through Pull Requests, with CI validating the combined candidate and its Foundation/Hello/World dependencies before merge. CD deploys the accepted revision. Shared/private APEX development is an environment implementation choice underneath that flow, not a replacement for PR review. Revalidate when the PR or integration baseline changes. This is the implementor's technical recommendation for review, not a claim that APEX automatically supplies a Git/PR pipeline.

## Git authority, break-glass recovery and drift detection

Following the collaboration discussion, the Product Owner retained native Working Copies as a break-glass mechanism. Normal integration uses task branches, PR validation and controlled deployment. Earlier descriptions of shared DEV/native merge are researched alternatives, not the selected release path. A native Working Copy remains live in APEX and linked to Main; export creates files, including a selected subset if requested. A copy does not isolate business tables/data. The native merge is not a substitute for our PR/deployment controls.

For drift, [APEX_EXPORT.GET_APPLICATION in 24.2](https://docs.oracle.com/en/database/oracle/apex/24.2/aeapi/GET_APPLICATION_Function.html) provides CHECKSUM-SH256, documented as independent of internal IDs across instances/ workspaces. It also exposes export date/audit and content-scope options. This supports proposing a reproducible live-target fingerprint. It does not establish an atomic change counter, schema drift coverage or a complete deployment lock. Record the recomputed target fingerprint after successful deployment, then recompute before the next one with the same profile. Timestamp/version labels are supporting metadata, not content proof. Coverage/stability after import, target mappings and manual edits remain E.1 experiments; none was run in I.1.

APEX application availability/build-status settings can restrict runtime or editing; [24.2 documentation](https://docs.oracle.com/en/database/oracle/apex/24.2/aeadm/changing-build-status-for-multiple-applications.html) distinguishes these controls. They do not supply our proposed inherited component/page states or a lock honored by unrestricted administrators. Runtime state policy, deployment ownership, expected-revision checks and authorized emergency access must be designed together. The separate architecture chapters specify this project policy and label unvalidated mechanics explicitly.

## Core multi-developer acceptance refinement

The A/B/C journey is core proof-of-concept scope: A authors Foundation, B and C author Hello/World independently, and a later concurrent request by B and C to modify Hello must have exactly one winner as early as managed task acquisition. The implementor proposes shared atomic component reservation in UC-9, before task branch/developer-area preparation. Earlier investigation of mergeable independent pages within the same module is superseded by this deliberately coarser component-ownership policy for normal tasks. Native conflict resolution remains relevant to break-glass/out-of-tool reconciliation. Git/PRs, reservation ownership, runtime state and deployment locks have separate responsibilities. This is a project design proposal; no claim is made that APEX or Git supplies the reservation control natively or that the scenario has run.
