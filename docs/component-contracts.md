# Component contracts and semantic versions

## Authority and delivery unit

[SRS](srs.md) owns requirements and [architecture](architecture.md) owns delivery mechanisms. This document owns explicit component promises and classifications. [The E.6 design](../progress/E.6/sprint_E.6_design.md), [walkthrough](../progress/E.6/sprint_E.6_increment_demo.md) and [executed tests](../progress/E.6/sprint_E.6_tests.md) connect those promises to the bounded experiment. [The declarations](../examples/secure-backend/contracts.json) record selected component versions and dependency ranges. They are reviewed declarations, not automatic compatibility inference or a new dependency resolver.

One whole application and its database source remain the native deployment unit. Application release 1.0.0, migration E6_SCHEMA_001 and Greeting component contract 1.1.0 are distinct identities. A component version does not imply selective deployment, automatic migration or consumer independence. Native packaging remains pinned to approved SQLcl 25.4.1.0 / build 25.4.1.022.0618. A tag for another Git state requires that state's approved toolchain.

## Observable promises

Greeting 1.x supports named render(p_text) calls returning “Hello ” followed by trimmed text, with -20410 for blank or overlength input. The 1.1 suffix argument is optional, so existing positional and named calls remain valid. hello(p_name) is deprecated but callable throughout 1.x; removing it requires 2.0 and a consumer migration. The opt-in render_v2 returns structured JSON without replacing the legacy result. Ordinary rendering does not depend on an APEX session.

CountryPolicy 1.0 supports PL and DE. A session-dependent request requires a native APEX session in app 810603, an enabled identity/country permission and a matching P1_COUNTRY item. The country argument is untrusted. Initialization errors propagate; session creation with a supplied username is privileged fixture setup, not proof of password authentication. Schema owners and administrators remain trusted. Tests do not establish resistance to an attacker with arbitrary parsing-schema code execution.

Request 1.0 writes one request and one corresponding audit row in a single caller transaction. A country/request-key pair is unique. A duplicate is rejected with -20403; no silently overwritten request, autonomous audit or internal commit is promised. On failure, rollback to the operation's savepoint preserves prior caller work, while successful work remains subject to caller commit/rollback. Concurrent unique-key inserts can wait: if the winner commits, the waiter receives the duplicate error; if it rolls back, the waiter can succeed. The experiment bounds client waits and measures those two interleavings only. It does not promise general exactly-once delivery, fairness, retries, cancellation or all isolation levels.

## Representative classification review

A whitespace fix that restores the documented trimmed text is a patch (1.0.0 → 1.0.1); the defect is in implementation, not a revised promise. Existing valid World consumers pass before and after, and the fixed padded-text behavior is checked separately. An optional suffix and a separate opt-in JSON operation are minor additions (1.0.1 → 1.1.0): unchanged named and deprecated calls retain their results and errors. A JSON result substituted for the existing text result is major, even if its SQL signature still compiles; executable consumers detect it. Removing/renaming a required argument or legacy callable, changing documented errors, adding an internal commit or changing caller rollback behavior likewise requires a major contract decision, not a patch label.

For a shared country LOV, stable stored codes and their meaning are contractual. Adding ES while preserving PL/DE is a minor LOV extension only when dependent policy/schema/application versions also support ES; adding a choice alone cannot make unsupported writes compatible. Deleting DE, reusing PL for another country or changing a default relied on by consumers is major. A spelling correction to a display label is patch only when the contract explicitly excludes label text from identity and consumers do not parse it; otherwise compatibility must be established first. APEX item names, requests, validation associations and supported navigation are also interfaces: renaming P1_COUNTRY without adapting every caller is major; a layout-only change preserving those interfaces is patch.

Retained-data promises are reviewed separately from syntax. A lossless additive representation can be minor after migration validation; discarding rows, reinterpreting stored country codes or changing how prior records render is breaking even when the new code compiles. E.6 does not validate a populated upgrade: the already planned E.7/E.12–E.14 experiments own those proofs. Version ranges express which component contracts a release was reviewed against; they do not replace executable consumer, data-preservation or native packaging checks.
